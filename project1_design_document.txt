---- DATA STRUCTURES ----

>> A1: Copy here the declaration of each new or changed `struct' or
>> `struct' member, global or static variable, `typedef', or
>> enumeration.  Identify the purpose of each in 25 words or less.
1. In timer.c
static struct list sleep_list : this carry the threads interrupted by timer_sleep.
2. In thread.h
struct list_elem sleepelem : used as a marker for sleep_list.
int64_t waketime : mark the time that a thread should wake + check if time_slice has passed

---- ALGORITHMS ----

>> A2: Briefly describe what happens in a call to timer_sleep(),
>> including the effects of the timer interrupt handler.
1. Timer_sleep() record waketime as current time + input ticks, then 
disable interrupt, change the status as blocked, and schedule a new thread.
2. Timer interrupt handler scan the sleep_list for element with waketime less than current time, 
unblock them and put them in the ready_list, then make it execute thread_yield() later.

>> A3: What steps are taken to minimize the amount of time spent in
>> the timer interrupt handler?
It doesn't try to wake the threads all the time.
Rather, it try to wake the threads in sleep list when time_slice has passed 
or if the current thread is idle.

---- RATIONALE ----

>> A6: Why did you choose this design?  In what ways is it superior to
>> another design you considered?

1. We used this design to minimize the change in the template.
but a new member of struct thread waketime must be needed to find when a thread wakes up.

2. We thought of adding THREAD_SLEEP in the thread's status. 
But, the template was made to check the thread's status, 
so if we did so. we should have looked at & changed the codes provided. 
However, by creating sleep_list and sleepelem, we were 
able to minimize the change, thus enabling ourselves to minimize the error posibilities.

>> B7: Why did you choose this design?  In what ways is it superior to
>> another design you considered?

our design keeps ready_list to be always ordered by using list_insert_ordered.
then what we have to do become simple.
when we push a thread to ready_list, we just use list_insert_ordered.
And we try to pop a thread from the ready_list, we just pop from the front.

if we chose another design, then we should have compared and recorded the index
while using list_insert_ordered only compared the priority in between.
Thus our design became simpler and efficient.
