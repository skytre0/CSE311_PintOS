            =====================

>> `struct' member, global or static variable, `typedef', or

In vm/page.h

struct supplemental_page{
    struct file* file;

    uint32_t zero_bytes;

---- ALGORITHMS ----

>> A2: In a few paragraphs, describe your code for accessing the data
>> stored in the SPT about a given page.

each process has SPT in struct thread.
and our SPT is hash map.
we implemented spt_find_page  function find exact SPT element by utilizing hash_find and hash_entry which are provided.


>> A3: How does your code coordinate accessed and dirty bits between
>> kernel and user virtual addresses that alias a single frame, or
>> alternatively how do you avoid the issue?

we used "||" operation to check both kernel and user address each time it was chosen.


---- SYNCHRONIZATION ----

>> A4: When two user processes both need a new frame at the same time,
>> how are races avoided?

frame_alloc function allocates a frame. And frame_alloc function use lock, so only one thread can allocates at a time.
And after allocation, the other tries to allocate a frame.

---- RATIONALE ----

>> A5: Why did you choose the data structure(s) that you did for
>> representing virtual-to-physical mappings?

our Supplemental Page Table implemeted as hash map.
so, we can access the information about mapping very fast.
if we use linked list, searching time would take O(n). but map can do faster.


               PAGING TO AND FROM DISK
               =======================

---- DATA STRUCTURES ----

>> B1: Copy here the declaration of each new or changed `struct' or

>> enumeration.  Identify the purpose of each in 25 words or less.


In vm/swap.h
static struct block *swap_block;

static struct lock swap_lock;

swap block for swap disk, bitmap to check if the block is empty or not, lock for synchronization.


---- ALGORITHMS ----

>> B2: When a frame is required but none is free, some frame must be
>> evicted.  Describe your code for choosing a frame to evict.

frame_evict function choose evicted frame.
we use clock algorithm.

Since we use linked list for frame table.
frame_evict function pop the first element of list. and push back it to the list.
then it tries to search like clock.

for each search, pagedir_is_accessed functino check access bit. and by using this if access bit was 0, then it eviceted.
else, set access bit to 0.





>> B3: When a process P obtains a frame that was previously used by a
>> process Q, how do you adjust the page table (and any other data
>> structures) to reflect the frame Q no longer has?
we used pagedir_clear_page, and adjusted the arguments one at a time without calling other functions by overwriting.


>> B4: Explain your heuristic for deciding whether a page fault for an
>> invalid virtual address should cause the stack to be extended into
>> the page that faulted.

check if it is not less than 32 bytes than esp, since it is only user, and check if 
it is less than 8MB from PHYS_BASE.

---- SYNCHRONIZATION ----

>> B5: Explain the basics of your VM synchronization design.  In
>> particular, explain how it prevents deadlock.  (Refer to the
>> textbook for an explanation of the necessary conditions for
>> deadlock.)

In our implementation, there is no cycle.
we have set the order, and there is no overlapping locks.

>> B6: A page fault in process P can cause another process Q's frame
>> to be evicted.  How do you ensure that Q cannot access or modify
>> the page during the eviction process?  How do you avoid a race
>> between P evicting Q's frame and Q faulting the page back in?

we used boolian value "pin" to ensure that other process could not remove the target frame.
when it is true, and only the process P can make it false.
pined frame is never eviceted.

>> B7: Suppose a page fault in process P causes a page to be read from
>> the file system or swap.  How do you ensure that a second process Q
>> cannot interfere by e.g. attempting to evict the frame while it is
>> still being read in?

we also used pin to make sure that other processes could not interfere with the process, like B6.


>> B8: Explain how you handle access to paged-out pages that occur
>> during system calls.  Do you use page faults to bring in pages (as
>> in user programs), or do you have a mechanism for "locking" frames
>> into physical memory, or do you use some other design?  How do you
>> gracefully handle attempted accesses to invalid virtual addresses?

we used locking to to make sure the pages need for that syscall should never leave the frame, 
thus pinning all need pages in the frame.

---- RATIONALE ----

>> B9: A single lock for the whole VM system would make
>> synchronization easy, but limit parallelism.  On the other hand,
>> using many locks complicates synchronization and raises the
>> possibility for deadlock but allows for high parallelism.  Explain
>> where your design falls along this continuum and why you chose to
>> design it this way.

we used frame_lock for frame, filesema for file, swap_lock for bitmap for parallelism.

---- ALGORITHMS ----

>> C2: Describe how memory mapped files integrate into your virtual
>> memory subsystem.  Explain how the page fault and eviction
>> processes differ between swap pages and other pages.

it can be accessed with read or write system call. if it is read, only access bit is set. else, 
access bit is set, and dirty bit is also set. when it is chosen for eviction, if it is only read, discard it
since no change is made. if it is dirty, apply the change to the file without saving it to the disk.

>> C3: Explain how you determine whether a new file mapping overlaps
>> any existing segment.

we used pg_round_down to make sure there was no overlapping with the file.

---- RATIONALE ----

>> C4: Mappings created with "mmap" have similar semantics to those of
>> data demand-paged from executables, except that "mmap" mappings are
>> written back to their original files, not to swap.  This implies
>> that much of their implementation can be shared.  Explain why your
>> implementation either does or does not share much of the code for
>> the two situations.

it is almost half to half since there can be file, stack data, or mmap, and 
if it is only read, mmap and file share the same method.
else, mmap is different from those two. so to determine this, we used if ~ else
method, thus almost creating half similarity.
